## 1. 전체 아키텍처

```
                 무료 REST (세션 종료 +30분 후 = historical)
  OpenF1 API ─────────────────────────────────┐
                                              ▼
                     ┌────────────────────────────────────────┐
                     │  수집기 repo (비공개) · GitHub Actions   │
                     │  체크 잡(1일 2회) → 미수집 세션 발견 시    │
                     │  백필 잡: 수집 → 검증 → gzip → 업로드     │
                     └───────────┬───────────────┬────────────┘
                                 ▼               ▼
                  Cloudflare R2            Firestore (Spark)
                  리플레이 gz 청크           세션 인덱스·매니페스트
                                 │               │
                                 ▼               ▼
                        브라우저 (React SPA) ← Vercel Hobby ← 앱 repo (공개)

  ─ ─ ─ 라이브 업그레이드 시에만 (§8) ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─
  OpenF1 MQTT ─(스폰서 €9.90)→ Actions 라이브 잡 → RTDB → 브라우저 실시간 구독
```

데이터 흐름 3종:
1. **수집(쓰기)**: Actions 잡이 OpenF1 REST를 rate limit(30 req/min) 내로 호출 → 엔드포인트별 gzip 파일을 R2에 업로드 → Firestore에 세션 매니페스트 기록. 쓰기 자격증명(R2 키, Firebase 서비스 계정)은 수집기 repo의 GitHub Secrets에만 존재.
2. **리플레이(읽기)**: 브라우저가 Firestore에서 세션 목록/매니페스트를 읽고, R2에서 청크를 직접 fetch. R2는 이그레스 0원이라 시청 횟수와 비용이 무관.
3. **라이브(예약)**: 지금은 비활성. 활성화 시 MQTT 수집 → RTDB 릴레이 경로가 추가될 뿐 1·2번 경로는 그대로다.

브라우저에서 OpenF1를 직접 호출하는 경로는 **탐색 최신화 보조용으로만** 허용(예: `sessions?year=` 신선도 확인 — CORS 지원 [실측], API ref §3.3). 리플레이 재생 데이터는 항상 R2에서 온다 — OpenF1 원 API의 rate limit·다운타임에서 시청 경험을 분리하는 것이 이 아키텍처의 목적.

## 2. 컴포넌트 상세

### 2.1 프론트엔드 — Vercel Hobby [확정]
- 앱 repo(공개, **개인 계정 소유**)를 Vercel에 연결해 push 시 자동 배포. Hobby는 **조직(organization) 소유 repo 연동 불가** [공식].
- 무료 한도 vs 예상: 전송 100 GB/월 ↔ SPA 번들 수 MB × 3명 ≈ 1 GB 미만. 배포 100회/일, 소스 업로드 100 MB — 여유.
- 서버 코드 없음(순수 정적 SPA). Vercel 함수는 사용하지 않는다 — 최대 60초 제한이라 수집기 용도로 쓸 수 없고 [공식], 쓸 이유도 없다.
- **비상업 전용** 플랜 [공식] — soon-board는 개인·비상업이므로 적합 (OpenF1 라이선스 CC BY-NC-SA의 비상업 조건과도 정합, §7).
- 한도 초과 시 과금이 아니라 **일시 중지**(다음 주기까지) — 요금 폭탄 리스크 없음.

### 2.2 리플레이 저장소 — Cloudflare R2 [확정]
- 무료 티어(카드 등록 불필요, 만료 없음) [공식]: 저장 **10 GB-월**, Class A(쓰기·목록) 100만/월, Class B(읽기) 1,000만/월, **이그레스 항상 0원**.
- 예상 사용: 3시즌 ~1.5 GB(15%) + 시즌당 +0.5 GB (§4). 읽기·쓰기는 한도의 0.1% 미만.
- 버킷 1개(`soonboard-replay`). 객체는 gzip 상태로 업로드하고 `Content-Encoding: gzip` + `Content-Type: application/json` 메타데이터를 설정 → 브라우저 fetch 시 투명 해제.
- CORS 정책: `GET`/`HEAD`, 오리진 = Vercel 도메인(+ localhost 개발용).
- 공개 접근: 개발·초기엔 **r2.dev 공개 개발 URL** 사용. r2.dev는 레이트리밋이 있고 프로덕션 비권장 [공식]이지만 시청자 3명 규모에선 실용상 충분. 운영 전환 옵션(§9 미정): 무료 Cloudflare Worker(workers.dev, 10만 req/일)로 버킷 바인딩 프록시, 또는 커스텀 도메인.

### 2.3 메타데이터 — Firestore (Spark) [확정]
- 무료 쿼터 [공식]: 저장 1 GiB, 읽기 5만/일, 쓰기 2만/일. **무료 쿼터는 `(default)` 데이터베이스에만 적용** — 명명 DB를 만들지 말 것.
- 리전: 생성 시 1회 선택·변경 불가 → `asia-northeast3`(서울) 권장.
- 예상 규모: 3시즌 ≈ 미팅 ~75 + 세션 ~370 + 매니페스트 ~370 → **1천 문서 미만**, 화면 진입당 읽기 수십 건 — 쿼터의 1% 미만.
- 보안 룰: **읽기 공개, 클라이언트 쓰기 전면 금지** (쓰기는 수집기의 서비스 계정만). 클라이언트 SDK에 노출되는 Firebase config는 비밀이 아님(룰이 방어선).
- 문서 설계는 §3.3.

### 2.4 라이브 릴레이 — Realtime Database (예약, 현재 미생성)
- 라이브 업그레이드 전까지 **인스턴스를 만들지 않는다** — 리전 선택이 생성 시 1회뿐이므로 [공식] 결정을 라이브 시점으로 미룬다.
- 리전 후보 [공식]: `us-central1` / `europe-west1` / `asia-southeast1`(싱가포르, 한국 최근접). Spark 플랜에서 리전 선택이 제한되면 `us-central1`로도 무방 — 1 Hz 릴레이에 왕복 ~180 ms는 체감 무영향(피드 자체가 ~3초 지연).
- Spark 무료 [공식]: 저장 1 GB, 다운로드 10 GB/월, 동시 접속 100. 예상 사용은 §8.

### 2.5 수집기 — GitHub Actions (비공개 repo) [확정]
- 비공개 repo 무료 2,000분/월, 잡당 최대 6시간 [공식]. 스케줄 실행은 수 분 지연될 수 있음 [공식] → 시각에 여유를 두고 설계.
- F1 세션 시각은 주말마다 달라 고정 cron으로 세션을 직접 겨냥하지 않는다. 대신:
  - **체크 잡** (cron, 1일 2회: 00:00·12:00 UTC, ~1분): `sessions?year=`로 "종료 +30분이 지났고 아직 매니페스트가 없는 세션"을 스캔 → 있으면 백필 잡 트리거.
  - **백필 잡** (세션당 ~3분): REST 수집(2.1초 간격 = 30 req/min 준수) → 검증(§6.2) → gzip → R2 업로드 → Firestore 매니페스트 커밋.
- 월 소모 추정: 체크 60분 + 레이스 주말 3개 × 5세션 × 3분 ≈ **월 ~100–120분 (한도의 6%)**.
- 일회성 과거 백필(2024·2025 + 2026 경과분 ≈ 주말 ~60개): 약 **900분(15시간)** — 월 한도 내 일괄 가능, 잡 여러 개로 분할·최신 시즌부터 역순 실행 (§6.1).
- Secrets: `R2_ACCESS_KEY_ID`/`R2_SECRET_ACCESS_KEY`, `FIREBASE_SERVICE_ACCOUNT`, (라이브 시) `OPENF1_USERNAME`/`OPENF1_PASSWORD`.

### 2.6 repo 구조 — 2-repo 분리 [확정]
| repo | 공개성 | 내용 | 연동 |
|---|---|---|---|
| `soon-board` (현재 repo) | **공개** | React 앱 + docs | Vercel 자동 배포 |
| `soon-board-collector` | **비공개** | 수집·백필 스크립트, Actions 워크플로 | R2·Firestore 쓰기 |

- 수집기를 비공개로 두므로 Actions는 2,000분/월 한도를 따른다 — 리플레이 전용 운용(~120분)엔 충분하고, 라이브를 켜도 퀄리+레이스 수집(~1,000분/월)까지는 수용 (§8). 전 세션 라이브 수집이 필요해지면 그때 수집기 repo만 공개로 전환하면 된다.

## 3. 데이터 저장 설계

### 3.1 저장 범위 [확정]

| 포함 (화면 구동용 전부) | 제외 | 제외 사유 |
|---|---|---|
| `location` (3.7 Hz 원본, 전 드라이버) | `car_data` | PRD 텔레메트리 범위 제외. 포함 시 용량 2배 (§4) |
| `intervals` (레이스만 — 예선엔 404가 정상, API ref §8.5) | `team_radio` | PRD 범위 제외 + 2026 커버리지 급감 |
| `laps` `position` `race_control` `weather` `pit` `stints` | `starting_grid` | 대부분의 레이스에서 404 [실측] — 그리드는 예선 결과·초기 position으로 파생 |
| `session_result` `drivers` | `overtakes` `championship_*` | PRD 화면에 없음. 추월은 `position` 변화로 파생 가능. 필요 시 청크 추가만 하면 됨 |
| `sessions`/`meetings` 메타 (Firestore 인덱스로) | 프리시즌 테스트 세션 | 화면 대상 아님(기본값). 포함하려면 테스트 1개당 ~수백 MB(raw)로 큼 — 필요 시 별도 결정 |

- location은 **다운샘플 없이 원본 보존** [확정] — 서킷 맵 마커의 원천이고, 압축 후 용량이 충분히 작다.

### 3.2 청크 포맷·경로 규칙
- 객체 키: `replay/{year}/{meeting_key}/{session_key}/{endpoint}.json.gz`
  - 예: `replay/2026/1290/11334/location.json.gz` (~7.2 MB), `.../intervals.json.gz` (~0.3 MB)
- **엔드포인트별 세션 단위 통파일** — 레이스 리플레이 진입 시 총 ~7.5 MB(gz)를 병렬 fetch. 일반 회선에서 1~3초, 이그레스 0원이라 재방문 부담 없음. 스크럽 즉시성이 부족하면 `location`만 10분 버킷 분할로 후속 최적화 [미정 — design 단계에서 UX 보고 판단].
- 내용은 OpenF1 응답 JSON 배열 그대로(무가공 보존) — 파생·가공은 전부 클라이언트에서. 원본 보존이 곧 스키마 진화 대비책이다.
- 압축률 실측 [실측]: location 12.8× · intervals 11.6× · laps 14× · 예선 location 19× (gzip -9).

### 3.3 Firestore 문서 설계 (초안)
```
meetings/{meeting_key}     — 이름·국가·서킷·연도·date_start/end (탐색 허브 목록용)
sessions/{session_key}     — meeting_key, session_name/type, date_start/end,
                             status: collected|missing|partial,
                             chunks: { endpoint: {key, bytes, rows} },  ← 매니페스트
                             collected_at, driver_count
```
- 프론트 탐색 흐름: `meetings`(연도 필터) → `sessions`(meeting_key 필터) → 매니페스트의 청크 목록으로 R2 fetch.
- 인덱스 신선도: 수집기 체크 잡이 매일 `sessions?year=` 결과를 upsert — 클라이언트는 OpenF1를 몰라도 된다.

### 3.4 서킷 지오메트리 정적 자산 [2026-07-28 추가]

세션 청크와 달리 **서킷·연도 단위로 한 번만 만들고 재사용하는 작은 자산**이다. 트랙 맵 오버레이(섹터 경계·마셜 섹터·코너 번호·DRS zone)와 퀄리 미니섹터 갭 계산이 전부 여기에 의존한다.

- 객체 키: `circuit/{year}/{circuit_key}.json.gz` — MultiViewer 서킷 JSON 원본 스냅샷 (Spa 19.7 KB raw). 소스는 `meetings.circuit_info_url`이며 **`location`과 좌표계가 동일해 affine 변환이 불필요하다** [실측, API ref §6.2.1].
- 왜 R2에 넣는가: MultiViewer는 OpenF1보다도 보장이 없는 서드파티다. 시청 경로를 외부 API에서 분리하는 §1의 원칙을 그대로 적용한다. 24서킷 × 3시즌 × ~20 KB ≈ **1.5 MB** — 용량 무관.
- 객체 키: `circuit/{year}/{circuit_key}.drs.json.gz` — **DRS zone 도출 결과** (zone별 detection / activation_start / activation_end를 arc-length로). 수집기가 `car_data?drs>=10` / `?drs=8` 범위 필터로 필요한 표본만 받아(세션·드라이버당 24~57 KB) 도출하므로 **`car_data` 전량 저장 없이** 만들 수 있다 — §3.1의 제외 결정은 유지된다.
  - **2023~2025 세션만 생성된다.** 2026은 `car_data.drs`가 전부 null이고 `category='Drs'`도 404여서 소스가 없다 [실측, API ref §8.9]. 2026 이후는 오버레이를 "데이터 없음"으로 표시한다.
  - 참고: 이 도출 로직은 `origin/personal_page` 브랜치에 이미 구현·검증되어 있다 (`scripts/_lib/drsZonesDeriver.ts` + `drsZones_2-{2023,2024}.json`, 전이 264건 → zone 2개). 재사용할 것. 단 그 브랜치는 아웃라인 소스가 julesr0y SVG여서 `applyOpenF1Transform` affine이 필요했는데, **MultiViewer로 바꾸면 그 단계가 사라진다.**
- 국적 표기용 `driver_number→국가` 정적 매핑도 앱 번들에 둔다 (`drivers.country_code`가 2026부터 null, 시즌 후 필드 제거 예정 — API ref §8.3).

## 4. 용량 — 실측과 전망

2026 Spa 주말(22대) 실 응답 크기 측정 [실측 — 근거: 수집 스크립트 `volume_probe.py`, 원본 응답 보관]:

## 6. 운영 절차

### 6.1 일회성 과거 백필 (구현 후 1회)
1. 대상: 2024·2025 전 주말 + 2026 경과 주말 (~60개, GP만·테스트 제외).
2. 최신 시즌부터 역순(2026 → 2024) — 먼저 쓸 데이터부터 확보.
3. 세션당 호출 ~31건(드라이버별 location 22 + 나머지 엔드포인트 9)을 2.1초 간격으로 — 세션 ~3분, 주말 ~15분, 전체 ~900분. Actions 잡을 시즌·구간별로 분할해 6시간 한도 회피.
4. **404 = "데이터 없음"이 정상** (예선 intervals, 2023-스타일 필드 등 — API ref §3.2) — 오류로 집계하지 말 것.
5. 완료 후 매니페스트 `status`로 누락 세션 리포트 → 수동 재시도.

### 6.2 주말 자동 운영
체크 잡(1일 2회)이 미수집 종료 세션 발견 → 백필 → 업로드 전 무결성 검증:
- 각 청크 rows > 0 (단, intervals는 레이스만 존재 — 비레이스에서 404면 정상 결측으로 매니페스트에 기록)
- `location` rows ≈ 드라이버 수 × 세션 길이(초) × 3.7 Hz ± 40% — 크게 벗어나면 `partial` 마킹 후 다음 체크 주기에 재수집 (OpenF1 라이브 수집 실패 시 historical이 늦게 채워지는 전례 [커뮤니티, API ref §5.4] 대비)
- 업로드 → 매니페스트 갱신은 마지막에 (매니페스트 존재 = 시청 가능 보장)

### 6.3 모니터링·알림
- Actions 실패: GitHub 기본 이메일 알림으로 충분.
- R2 저장량·요청 수: Cloudflare 대시보드 분기 1회 육안 확인.
- Vercel 사용량: 대시보드 (100 GB 근접 시 이메일 옴).
- OpenF1 장애 시(SLA 없음, 전면 다운 전례 [커뮤니티]): 수집은 재시도로 자연 복구되고, 시청 경로는 R2라 **기존 리플레이는 OpenF1 다운과 무관하게 동작**한다.

### 6.4 구현 검증 원칙
각 story 완료 시 회귀 체크(프로젝트 메모리의 5종 체크리스트)를 적용한다: 실 endpoint cross-check(404 경로 포함) · hooks-before-early-return · 형제 컴포넌트 일관성 · `npm run dev` 실진입 + console 에러 0 · 정적/R2 fetch가 SPA fallback이 아닌 실 JSON 200인지.

## 7. 보안·라이선스 제약

- **OpenF1 라이선스 CC BY-NC-SA 4.0**: 비상업 유지(수익화·광고 금지), 앱 푸터에 OpenF1 출처 표시, 데이터 재배포 시 동일 조건. Vercel Hobby의 비상업 조건과 방향이 같다.
- 쓰기 자격증명(R2 키, Firebase 서비스 계정)은 **수집기 repo(비공개)의 GitHub Secrets에만** 존재. 앱 repo(공개)와 클라이언트 번들에는 어떤 쓰기 권한도 넣지 않는다.
- Firestore 룰: 읽기 공개 / 쓰기 금지(서비스 계정 예외). R2: 공개 읽기 전용 노출(쓰기는 API 키).
- (라이브 시) OpenF1 계정·토큰은 수집기에만 — 클라이언트에 토큰을 전달하지 않는 백엔드 릴레이 구조가 공식 보안 권고와 일치 (API ref §2.4).

## 8. 라이브 업그레이드 경로 (지금은 비활성 [확정])

아키텍처 변경 없이 다음 스위치만 켜면 된다:

1. OpenF1 스폰서 가입(€9.90/월) → 수집기 Secrets에 계정 등록. 토큰은 1시간 만료라 수집 잡 내부에서 갱신 (API ref §2.1).
2. RTDB 인스턴스 생성 (리전 결정 — §2.4).
3. 수집기에 라이브 잡 추가: 세션 시작 30분 전 기동(Actions cron은 주말 시간대 + 잡 시작 시 세션 유무 확인 패턴) → MQTT(`mqtts://mqtt.openf1.org:8883`) 구독 → `_key` upsert 규칙으로 상태 집계 (API ref §2.3) → **1 Hz로 RTDB에 릴레이** (리더보드·간격·맵 좌표·플래그·날씨 스냅샷, ~2 KB/s) → 종료 후 즉시 청크화·R2 업로드(리플레이 즉시 가능).
4. 프론트 라이브 셸이 RTDB를 구독. PRD의 "방송류 ~30초 지연"은 클라이언트 표시 버퍼로 구현(피드 자체 지연 ~3초 + 선택 버퍼).
- 예산 영향: 퀄리+레이스만 수집 시 Actions ~1,000분/월(비공개 한도 내), RTDB 다운로드 ~0.3 GB/월(한도 10 GB). 전 세션 라이브 수집은 2,000분 초과 → 수집기 repo 공개 전환 필요.
- [미실측] 라이브 윈도우 중 **무인증** REST가 정확히 무엇을 받는지(401 vs 빈 응답)는 미확인 — 라이브 활성화 전에 아무 세션에서나 1콜로 실측해 프론트 오류 처리에 반영할 것.
